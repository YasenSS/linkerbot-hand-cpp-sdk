# O6 Feature Guide

O6 has 6 joints. The SDK defaults to the original O6 Classic CAN protocol; for firmware running **HOP 0.0.4**, explicitly set `config.o6_protocol`.

This page uses the C++ `HandDevice` API for common operations.

## Usage

Before starting, set up your build environment and CAN interface as described in [Prepare the communication interface](../connections/prepare-interface.md).

### Match the three protocol modes first

The **device's current mode**, the **host CAN interface**, and **`config.o6_protocol` in code** must all match. Otherwise, `hand.open()` will time out (`device request deadline expired`):

| Protocol mode | `config.o6_protocol` | Default CAN ID | Linux `can0` setup |
| --- | --- | --- | --- |
| Classic (legacy default) | `O6Protocol::kClassic` (default) | Left `0x28` / Right `0x27` | `bitrate 1000000 fd off` |
| HOP 0.0.4 · CAN FD | `O6Protocol::kHopV004` | Request `0x001` / Response `0x401` | `bitrate 1000000 dbitrate 5000000 fd on` |
| HOP 0.0.4 · CAN 2.0 | `O6Protocol::kHopV004Can` | Request `0x001` / Response `0x401` | `bitrate 1000000 fd off` |

### Minimal complete program (Linux SocketCAN)

The example below connects to a Classic O6 and reads all 6 joint angles (for HOP firmware, set `o6_protocol` and `address` as shown in the next section; on Windows, supply an adapter transport factory—the feature calls stay the same):

```cpp
#include <chrono>
#include <exception>
#include <iostream>
#include <linkerbot/hand/api/device.hpp>

using namespace linkerbot::hand;
using namespace std::chrono_literals;

int main() {
    try {
        HandDeviceConfig config;
        config.model = Model::kO6;
        config.side = HandSide::kLeft;   // Change to kLeft or kRight as needed
        config.interface_name = "can0";

        HandDevice hand(config);
        hand.open();

        // Any feature snippet below can be placed here (after open() and before close())
        const auto angles = hand.get_angles(1s);
        for (const auto angle : angles.raw) {
            std::cout << angle << ' ';
        }
        std::cout << '\n';

        hand.close();
    } catch (const std::exception &e) {
        std::cerr << "Error: " << e.what() << '\n';
        return 1;
    }
    return 0;
}
```

> Tips:
> - `HandDevice`'s destructor automatically attempts to close the connection on scope exit, so a single `try / catch` block is enough to report errors clearly. For production close-retry and recovery patterns, see the [API guide](../guides/usage.md).
> - All `set_*` methods enqueue asynchronously and return a `CommandHandle`. Call `cmd.wait_for(2s)` and check `cmd.error()` when you need to confirm delivery/acknowledgement.
> - In production code, check `sample.meta.valid` and `sample.meta.stale` before using sensor samples.

## Manual HOP 0.0.4 connection

Connect to HOP firmware manually by specifying the hand side, request ID (default `0x001`; response ID is automatically `request_id | 0x400`), and the `o6_protocol` that matches the device's current frame format.

> `config.o6_protocol` only selects **which frame format the SDK uses**—it does not change the device's mode. To switch the device-side mode, see [Switching HOP CAN modes](#hop-can-mode).

### 1. Configure Linux SocketCAN

Choose the command matching the device's current CAN mode:

```bash
# Device currently in CAN FD (1 Mbit/s nominal + 5 Mbit/s data; SDK sends with BRS off)
sudo ip link set can0 down
sudo ip link set can0 up type can bitrate 1000000 dbitrate 5000000 fd on

# Device currently in CAN 2.0 (1 Mbit/s, FD disabled)
sudo ip link set can0 down
sudo ip link set can0 up type can bitrate 1000000 fd off
```

### 2. Read CAN configuration and angles (complete example)

```cpp
#include <chrono>
#include <exception>
#include <iostream>
#include <linkerbot/hand/api/device.hpp>

using namespace linkerbot::hand;
using namespace std::chrono_literals;

int main() {
    try {
        HandDeviceConfig config;
        config.model = Model::kO6;
        config.side = HandSide::kRight;
        config.interface_name = "can0";
        config.address = 0x001;
        config.o6_protocol = O6Protocol::kHopV004; // Use kHopV004Can if device is in CAN 2.0

        HandDevice hand(config);
        hand.open();

        const auto can = hand.get_can_configuration();
        std::cout << "request_id=0x" << std::hex << can.request_id
                  << " response_id=0x" << can.response_id() << std::dec
                  << " mode=" << (can.interface_mode == HopCanInterfaceMode::kCanFd ? "canfd" : "can")
                  << " nominal=" << can.nominal_bitrate
                  << " data=" << can.data_bitrate
                  << " brs=" << can.brs << '\n';

        const auto angles = hand.get_angles(1s);
        for (const auto angle : angles.raw) {
            std::cout << angle << ' ';
        }
        std::cout << '\n';

        hand.close();
    } catch (const std::exception &e) {
        std::cerr << "Error: " << e.what() << '\n';
        return 1;
    }
    return 0;
}
```

> **Troubleshooting timeouts**: If you get `device request deadline expired`, the most common cause is a **mismatch between the device's current mode and `config.o6_protocol`** (for example, code uses `kHopV004` while the hand is in CAN 2.0 mode), or swapped CAN_H / CAN_L lines. Temporarily switch `o6_protocol` to `kHopV004Can` (with `can0` set to `fd off`) and rerun to see which mode prints `mode=...` and confirm the device's current state.

## Switching HOP CAN modes

The device-side HOP frame format is controlled by register `MI 0x35 / SI 0x06` (`1` = CAN 2.0, `2` = CAN FD), and Flash save is triggered by `MI 0x35 / SI 0x1E = 1`.

Switching always follows three steps: **1. Check current mode → 2. Switch device-side mode → 3. Update the host interface and `o6_protocol`**.

### Step 1: Check the device's current mode (read-only)

Run the complete example in the previous section (which calls `hand.get_can_configuration()`) to print the current `mode=canfd` or `mode=can`, along with `brs` and bitrates. If unsure, try `kHopV004` (`fd on`) and `kHopV004Can` (`fd off`) once each.

### Step 2: Switch the device-side mode

> Note: Device-side `brs` must be `0` before switching to CAN 2.0. With `save_to_flash = false`, the change is volatile and reverts after a power cycle—verify communication before saving to Flash.

#### Option A: Call `set_can_interface_mode()` in your C++ program (recommended, works with the release package)

Open the device in its **current** mode, switch, close it, and reopen with the new `o6_protocol`:

```cpp
#include <exception>
#include <iostream>
#include <linkerbot/hand/api/device.hpp>

using namespace linkerbot::hand;

int main() {
    try {
        HandDeviceConfig config;
        config.model = Model::kO6;
        config.side = HandSide::kRight;
        config.interface_name = "can0";
        config.address = 0x001;
        config.o6_protocol = O6Protocol::kHopV004; // Match the device's CURRENT mode: kHopV004 (FD) or kHopV004Can (CAN 2.0)

        HandDevice hand(config);
        hand.open();

        // Target mode: HopCanInterfaceMode::kCan20 or HopCanInterfaceMode::kCanFd
        // 2nd argument save_to_flash: false = volatile, true = write to Flash
        const auto result = hand.set_can_interface_mode(HopCanInterfaceMode::kCan20, false);
        std::cout << "active_wire_is_fd=" << result.active_wire_is_fd << '\n';

        hand.close();
    } catch (const std::exception &e) {
        std::cerr << "Error: " << e.what() << '\n';
        return 1;
    }
    return 0;
}
```

> **Known Linux SocketCAN behavior (CAN 2.0 → CAN FD)**: When connecting with `kHopV004Can` and switching to `kCanFd`, a classic SocketCAN socket cannot receive the immediate FD reply and may throw `CAN FD frame cannot be sent on a classic link`. The switch command has usually already taken effect. Do not resend immediately—reconfigure `can0` with `fd on` and run the read example with `kHopV004` to confirm `mode=canfd`. If you want to persist it to Flash, call `set_can_interface_mode(HopCanInterfaceMode::kCanFd, true)` once from `kHopV004` mode.

#### Option B: Send raw HOP frames with `cansend` on Linux (no code required)

If `can-utils` is installed on Linux, you can switch modes directly with `cansend` (especially handy for switching CAN 2.0 back to CAN FD). For default `request_id = 0x001` (`#` sends a CAN 2.0 frame; `##0` sends a CAN FD frame with BRS off):

```bash
# CAN FD → CAN 2.0
cansend can0 001##035060101

# CAN 2.0 → CAN FD
cansend can0 001#35060102

# Optional: save to Flash (match the active format after switching)
cansend can0 001#351E0101     # while in CAN 2.0
cansend can0 001##0351E0101   # while in CAN FD
```

#### Option C (optional, source-tree builds only): `hop_can_mode` CLI example

> Prebuilt release packages do not include `examples/`. This option applies only if you cloned the `linkerbot-hand-cpp-sdk` source repository, and must be run from the **SDK source root**.

```bash
cmake -S . -B build -DLINKERBOT_BUILD_EXAMPLES=ON
cmake --build build --target hop_can_mode

# Read-only query (defaults to CAN FD; append --from-mode can for CAN 2.0)
./build/examples/hop_can_mode can0 o6 right --request-id 0x001

# CAN FD → CAN 2.0 (append --save to write to Flash)
./build/examples/hop_can_mode can0 o6 right --from-mode canfd --mode can

# CAN 2.0 → CAN FD (if it reports a classic-link error, verify with the FD query above)
./build/examples/hop_can_mode can0 o6 right --from-mode can --mode canfd
```

If the CLI exits with code `2`, the register was updated but replies still use the old format; verify again after a controlled device restart.

### Step 3: Update the host interface and code

Once the new device mode is active, align both `can0` and `config.o6_protocol`:

| Target mode | Host `can0` command | Code setting |
| --- | --- | --- |
| **CAN 2.0** | `sudo ip link set can0 down && sudo ip link set can0 up type can bitrate 1000000 fd off` | `config.o6_protocol = O6Protocol::kHopV004Can;` |
| **CAN FD** | `sudo ip link set can0 down && sudo ip link set can0 up type can bitrate 1000000 dbitrate 5000000 fd on` | `config.o6_protocol = O6Protocol::kHopV004;` |

## Joint order

The SDK reads and sets the 6 joints in this order:

| Number | Vector index | Joint name | Joint |
| ---: | ---: | --- | --- |
| 1 | `0` | `thumb_flex` | Thumb flexion |
| 2 | `1` | `thumb_abd` | Thumb abduction/adduction |
| 3 | `2` | `index` | Index finger |
| 4 | `3` | `middle` | Middle finger |
| 5 | `4` | `ring` | Ring finger |
| 6 | `5` | `pinky` | Little finger |

Use `caps.joints[index].name` from `get_capabilities()` as the authoritative joint name.

## Device identity

`get_device_info(1s)` actively queries and verifies device identity; `get_identity()` returns the cached identity for the current connection.

```cpp
const auto info = hand.get_device_info(1s);
std::cout << "Serial number: " << info.serial_number.value_or("unknown") << '\n';
std::cout << "Product: " << info.product_code.value_or("unknown") << '\n';
```

## Capabilities

`get_capabilities()` sends no control commands and lets you inspect the supported joint ranges and operations:

```cpp
const auto caps = hand.get_capabilities();
for (const auto &joint : caps.joints) {
    std::cout << joint.index << ": " << joint.name
              << " raw=" << joint.raw_angle_range.minimum
              << ".." << joint.raw_angle_range.maximum << '\n';
}
```

<a id="angle-control"></a>

## Angle control

Raw angles range from `0..255`, and percentages range from `0..100` (increasing in the same direction by default). Mechanical poses depend on the hand side and joint type—do not equate abduction/rotation endpoints with "bent/straight".

### Reading angles

```cpp
const auto angles = hand.get_angles(1s);
for (const auto raw : angles.raw) {
    std::cout << raw << ' ';
}
std::cout << '\n';
```

`angles.percent` holds a `std::optional<double>` per joint (do not substitute `0` when unavailable):

```cpp
const auto angles = hand.get_angles(1s);
for (const auto &p : angles.percent) {
    if (p) {
        std::cout << *p << "% ";
    } else {
        std::cout << "N/A ";
    }
}
std::cout << '\n';
```

### Setting raw angles (read → set → read)

`set_angles()` takes 6 `int32_t` values (`0..255`). This example reads the current angles as the starting target (edit `targets[0..5]` as needed), waits for completion, and reads back:

```cpp
const auto before = hand.get_angles(1s);

std::vector<int32_t> targets(before.raw.begin(), before.raw.end());
// targets[5] = 200; // Modify a safe target value as needed, e.g. pinky

const auto cmd = hand.set_angles(targets);
if (!cmd.wait_for(2s)) {
    throw std::runtime_error("set_angles timed out");
}
if (const auto err = cmd.error()) {
    std::rethrow_exception(err);
}

// Optionally sleep briefly for mechanical travel before reading back (#include <thread>)
// std::this_thread::sleep_for(500ms);
const auto after = hand.get_angles(1s);
for (const auto raw : after.raw) {
    std::cout << raw << ' ';
}
std::cout << '\n';
```

### Setting percentage angles

`set_percent_angles()` takes 6 `float` values (`0..100`). Replace the target values with a safe pose for your task:

```cpp
std::vector<float> targets(6, 50.0F);
const auto cmd = hand.set_percent_angles(targets);
if (!cmd.wait_for(2s)) {
    throw std::runtime_error("set_percent_angles timed out");
}
if (const auto err = cmd.error()) {
    std::rethrow_exception(err);
}
```

<a id="speed-control"></a>

## Speed control

### Setting speeds

Raw counts in `0..255` (not a confirmed physical rotational speed):

```cpp
const auto cmd = hand.set_speeds(std::vector<double>(6, 100.0));
if (!cmd.wait_for(2s)) {
    throw std::runtime_error("set_speeds timed out");
}
if (const auto err = cmd.error()) {
    std::rethrow_exception(err);
}
```

### Reading configured speeds

```cpp
const auto speeds = hand.get_configured_speeds(1s);
for (const auto v : speeds.raw) {
    std::cout << v << ' ';
}
std::cout << '\n';
```

> Note: HOP queries the device register directly. The legacy Classic protocol reads the write-response cache in the current connection, so call `set_speeds()` first.

<a id="acceleration"></a>

## Acceleration settings

### Setting accelerations

`set_accelerations()` takes 6 raw counts (`0..254` on Classic, where `0` encodes special maximum acceleration; `0..255` on HOP):

```cpp
const auto cmd = hand.set_accelerations(std::vector<double>(6, 100.0));
if (!cmd.wait_for(2s)) {
    throw std::runtime_error("set_accelerations timed out");
}
if (const auto err = cmd.error()) {
    std::rethrow_exception(err);
}
```

### Reading configured accelerations

Reads the configured acceleration setting rather than live measured acceleration:

```cpp
const auto acc = hand.get_configured_accelerations(1s);
for (const auto v : acc.raw) {
    std::cout << v << ' ';
}
std::cout << '\n';
```

<a id="sensor-reading"></a>

## Reading sensor data

### Reading currents

`get_currents()` reads raw measured-current counts (distinct from current-limit settings; do not label as mA without a verified scale):

```cpp
const auto currents = hand.get_currents(1s);
for (const auto v : currents.raw) {
    std::cout << v << ' ';
}
std::cout << '\n';
```

### Reading temperatures

Classic protocol reports degrees Celsius; HOP capabilities report raw counts:

```cpp
const auto temps = hand.get_temperatures(1s);
for (const auto v : temps.raw) {
    std::cout << v << ' ';
}
std::cout << '\n';
```

### Reading tactile matrices

Use `get_force({"fn"}, 1s)` to read five-finger normal-force matrices (Classic defaults to 5 fingers × 10×4; HOP reads shapes from each finger's sensor descriptor). Missing fingers are represented by `std::nullopt`:

```cpp
const auto force = hand.get_force(std::vector<std::string>{"fn"}, 1s);
const auto *fn = force.field("fn");
if (!fn) {
    std::cout << "fn: " << force.status("fn") << '\n';
} else {
    for (size_t finger = 0; finger < fn->raw.size(); ++finger) {
        std::cout << "finger " << finger << ": ";
        if (!fn->raw[finger]) {
            std::cout << "no data\n";
            continue;
        }
        for (const auto value : *fn->raw[finger]) {
            std::cout << value << ' ';
        }
        std::cout << '\n';
    }
}
```

## Notes and known limitations

- **Command completion semantics**: `cmd.wait_for()` confirms communication dispatch or device acknowledgement only, not physical arrival. A wait timeout neither cancels nor resends the command. For strict `CommandStage` checks (`kAcknowledged`, `kDispatched`, `kSuperseded`, etc.), see the [API guide](../guides/usage.md).
- **Classic V1.3.2 speed query**: Do not call the native `speed.get_blocking()` query on Classic V1.3.2 firmware, as it may reset device speed to `0`; use `HandDevice::get_configured_speeds()` instead.
- **HOP mode switching and adapter boundaries**:
  - Current HOP CAN 2.0 requests leave the Classic frame format implicit; if `can0` stays in `fd on`, SocketCAN or MiniCANFD may transmit them as FD frames. Always set `can0` to `fd off` when using `kHopV004Can`.
  - Power-cycle persistence after `--save` and full adapter validation coverage are recorded in the [O6 HOP hardware record](../../hardware-acceptance/o6/report.md#o6-hop-2026-11-25).
- **More capabilities and units**: See [Model capabilities](../reference/model-capabilities.md).
